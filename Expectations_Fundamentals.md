1. The UI is organized around this fundamental heirarchy, with some 'system' Tables, notes below (Company, Projects, Users, etc) and with client-created [custom tables], and in most cases we will have some system tables the live on the same heirarchical level (e.g. Company>Projects>Shots)

- Company is at the top level example "Disney", etc., e.g. there is one company per URL / client and it is the one table that clients don't/can't customize
- Company>Events
  Company>Projects (e.g. "Toy Story 9", "Monsters, Inc. 11", "Finding Nemo, Jr.")
- Company>Assets
- Company>Users
- Company>Templates
- Company>Permissions (we start with some template permissions but these can be customized by clients, and/or they can create their own permissions)
- Company>[Custom Tables] (e.g. "Issues", "Documentation", etc.)
- Company>Projects>Shots, Assets, Departments, Steps, Phases, Versions, Tasks, Notes
- Company>Projects>[Custom Tables] (e.g. "Experimental Table", or "Quarks", or "Marketing Campaign", or "Reels")

2. The Projects level is where clients can create projects, each with distinct pipeline _types_, e.g. film, animation, manga, design, video games, etc. We have several pipleline-type templates that they can use to start with, or they can create their own, new, pipeline types. Important note: some templates will use a common table, like Shots, in different ways per project, for example in project "Nemo" the Shots table utilized a system drop-down selection field called 'Status' (even though it is a system field, it can be customized) with valid values of "Not Ready", "Ready to Start", "In Story", "In Layout", "In Animation", "In Comp/Light", and "Final"; while in project "Pirates" they only want "Ready to Start", "In Progress", and "Final Render Complete". In each, the statuses represent progress in each respective pipeline.

3. Related to above, there is a robust ability for the app to hide and show database fields and their nuances based on the project, template, and permissions. So we need a robust platform that tracks a lot of 'meta' data about the tables/fields/data.

4. The primary Navigation uses a Left Navigation tree structure based on heirarchy described here. Fundamental to this is the client's ability to create as many new Navigation destinations, or 'Saved Pages' as they like, and so the Nav needs a little intelligence: e.g. I create a new Saved Page where I specify I want to see all Shots across all projects, grouped by project -- upon creation, this should show up at the Company (above Project) level since it contains information about multiple, or all, projects. Later on, I can go into the Page Settings and adjust my query/filter settings, and If I narrow it to one project, that Page moves inside the Project

5. Continuation of 4 above: Clients can create 'folders' in the Nav that help them organize all the Pages that get built up -- a folder can only accept Pages in the same heirarchy: no breaking rules and putting one Project page inside a folder of a different project!

6. We embrace that clients want customizable colors and status names and icons, conditional colors (turn the bg of the shot row red if the due date is in the past), calculated columns, (the animation due date is the shot due date minus 4 weeks; or the 'total budget' field = the sum of three other fields; or the 'total bid' field = (the sum of all sub-bids) \* markup). We also have columns that can be configured to show summary data like 'sum', and 'avg' on numberic fields.

7. We embrace that pipleines are deeply integrated with other business logic and so our API is extremely robust, and key to that is our Event table, that tracks _every single thing_ that happens in the pipeline, knowing that clients rely on that to trigger other processes.

8. We embrace that production management (accountants, producers, 3rd party funders, studio executives, etc.) is going to need robust tools of their own to produce budgets, bids, progress reports, etc. We need to be really really sophisticated in how we allow the pipelines to be artist-centric, but at the same time give production management the numbers, stats, and scheduling/reporting/budgeting tools that they need.

9. We have some basic staples in our UI that the app uses:

- a 'table' Page view, which is data dense and pretty much a table view, and limited to one table
- a 'card' page view that can be flipped to from any table view, and it will display the data inside a collapsible widget, with more UI customizations available like which fields show in the title when collapsed, and what shows up with uncollapsed
- a 'dashboard' page that is configured to have x number of rows and columns and inside each users can select from the widget library which types of widgets to configure and display (e.g. pie charts, heat maps, histograms, bar charts, etc.)

10. We have all the usual field types, common in postgres, _and_ some specialized field types: query fields, calculated fields, Status fields (long display: "In Progress", a short display: "IP", and an icon that can be customized) and we have the concept of a "pipeline" which is stages/phases/steps/Departments that Shots or Assets (or other) go through. Different companies will want to use familiar names, we don't care... At the core a "pipeline" is just a series of Tasks organized in 'Steps' or 'Pipeline Steps', and sometimes they have two layers of organization, e.g. the "Shot Finaling" is a Department, around which an animation studio is organized (Shot Finaling has Manager, a Coordinator, etc.) but within this Department is where the pipeline steps of 'Sandbox', Lighting, Compositing, VFX, and Simulation all get scheduled, tracked, and completed. Sometimes a depart has only one step, for example 'Animation' department, may only schedule and track the step of 'Animation'. We accomodate this.

11. Specialized "Notes" tables. We have a system table called Notes, that is just what is sounds like: an email-like note (that users can subscribe to and get them also sent to their email). All users have an inbox with notes

12. Notifications: users have a robust notification where they can manage notification subscriptions to certain key things. At the most basic level, a note addressed to a person always shows up in their inbox, where it is just like an email, it is read or unread, we have basic meta data: who is is from, when it was timestamped, and if it was regarding something in production (e.g. a director note on an asset) we see a link to that thing. Notes also have their own set of statuses and when I get a note it is by default open and does not get closed until I close it manually. Notes are threaded just like emails and go back and forth. my inbox supports a gmail-like ability, so it is familiar (e.g. I can create smart folders to store different types of notes, e.g. by status, or by label, or by type )

13. More about Tasks: Tasks can be displayed as a gantt chart, Tasks can have Sub-Tasks, and both Tasks and Sub-Tasks can have 'To Do' lists. The data model allows Tasks and Sub Tasks to be assigned to individuals, but a 'To Do' list is more freeform with a simple binary checkbox to indicate if it is done or not, but with a Task-level summary of open 'To Do' items.

14. Themes. We will have several themes out of the box, knowing that artists prefer a very different, usually dark view, where management, producers, etc. prefer a light theme. Rule: each user can toggle their theme at will, and each theme has a light/dark toggle. BUT - we want the app to offer a 'theme designer' that allows companies to create their own themes/pick their own color scheme. Our themes ship and don't get changed, but companies can add to this (either starting from a copy of one of our themes, or start with a blank slate and pick each color one by one).

15. More about Table types and options:

- Tasks (including Sub tasks, which are also task, but the have a link in a field called 'Parent Task')
- Tables where has_tasks = true (Shots, Assets, determined per project)
- Tables where has_tasks = true and has_steps = true (Shots and Assets in some projects)
- Tables where has_tasks = true and has_steps = true and has_departments = true (Shots and Assets in some projects)
- Tables that are threaded (Issues, Notes)
- Tables where has_timecards = true (Timecard time can be logged agains these Tables, and they show up as 'Time Logged', in total hours, and if you click into the hyperlinked number you get a modal popup with a table view of the timecard records)

16. Detail Pages. A 'Detail Page' is an entire page dedicated to one record. These detail pages come templated in different flavors:

- the detail page of a record from a Threaded Table (Notes. Issues. looks like gmail, a conversation)
- the detail page of a record from a Table where has_tasks = true (Shots. Assets. has a gantt tab)
- Even though we present a template, users can adjust: add or remove tabs, right+click in the header to hide/show fields

17. Traversing links in the UI. An important power-feature is the ability to display fields, related to the current record/table by tracing through relationships.

18. Issues and Notes can be linked to many different entities. This is configurable by project. For example in my animation project, I want the note's 'link' field to be able to link to Tasks, Versions, Shots, Assets, People, Sequences and Departments. In another Teaser/Trailer project, I just want Notes to be able to link to Tasks. So this 'Link' field is very special, _and_ it can have many links. I also may have a Dev project where I want Issues to only be linked to Features or Bugs. You get the idea...

19. Admins can allow users to "Follow" things. Our Animation default will allow users to "Follow" Shots and Assets.

20. Conditional formatting of displayed records allows users with permissions to create formats based on conditions. Multiple conditions can be added; where the conditions are not mutually exclusive the order of condition decides the format. In the condition form, I pick a field, then a relational operator, and then define a value, or pick another value. For example, I define a condition: "Due Date", "<=" "Today"; and for the formatting I pick "font" becomes "red".  
    I can also make bg or border formats. After I select the first field, my options are smartly narrowed to what makes sense -- e.g. If I select a date field I need date options and tokens like "Today" or "Today + 7", or If I select a 'status' field, I then can pick from that fields list of values only so I can do things like "Status" = "Final".

21. Template Builder: Company admins have a special top-level module called 'Template Builder' -- used to build different workflows for all types of teams / indies everywhere. Need to organize yourself? Need to build a cabin? To organize a charity drive? To collect stamps? Need to shoot an indie live action film? Need to track budgets? Need to track outsourced contractors? Need to build a tract of homes? At the Template Builder level AI agents, in a side panel, Cursor-style, will help you by asking you a series of questions: "Give me a summary of what you are building, and a high level description of your workflow" The agent then dives deeper with the interview, knowing that some first timers will be describing things in their terms, while other advanced users will be very specific about the tables and relationships they want. The Agent then builds a flow chart (optional, advanced users can skip) and then a full-blow template project with some dummy-data, and continues to iterate with the user until the tempate is right, and all the while the template can be saved as a 'draft', it can be deleted, etc. When the user approves, it gets promoted into the official Templates section of the left nav.

or a thing that we have descriptions of in the absract: a agent (who is an expert in all things, and knows every last tool and piece of tech/code we have) interviews me and then asks me some key questions, and then pitches a workflow, when we accept, the agent creates the template inside the app, and we use it.. and then we can give the agent feedback on what is working / not working. Every template has to have dummy data so that is seems real and gives me something to really work with to pressure test how it holds up. If I describe a workflow that can't be accomodated, the Agent can submit feature requests.

22. Kanban view. The Kanban view will display records in columns, the default will be to display by status, but this can be configured to be any other field that is eligble: exclude plain text, id fields, but allow linked fields (e.g. sort Tasks by Sequence, or sort Shots by department, or sort Tasks by assignee, or sort Issues by Type). The records will by default be displayed in configurable cards, just like card view, and will also feature the same card component: "columns - 4 + " in the header which will determine the number of columns visible, and if the number of columns is more (e.g. there are 10 status and by default it sorts by status) then we have left and right indicators "<" and ">" (but icons, not the text chars - those are just for descriptive purposes in this doc) so that users can still move left and right in the kanban view.

23. Timecards. This app will offer a robust and top-of-class time card module. It is customizeable and will allow company admins to create time card rules based on unions, contracts, multiple unions on the same project (E.G. editors, voice actors, actors, stage crew, etc. all have different rules) and the company employees can log time towards assigned tasks and other approved activities (sick, vacation, etc.). Time card sophitication includes turnaround time, breaks, total hours per week, special rules for when overtime kicks in, 1.5x OT or 2x OT, holdiday OT, violation flagging, etc. etc., and artists will have an intelligent time card that is almost pre-filled for them, waiting for their approval, based on knowing where they were working in the app. Managers or salaried employees will also have a smart time card that intelligently infers their timecard (they get a salary, but most companies still want to know where to allocate their costs)... Placeholder (TBD) is that timecard data is a table of its own, becuase most companies will want an easy way to export all timecards for a period. We will have a robust tool for payroll departments to manage each payroll period: who has not completed their timecard? How much time before payroll gets processed and who needs to get a critical alerts? We will build / make possible integrations with intuit, adp, etc., all major payrol processing companies, and we will also build our own payroll processing module for companies who want to process their own (this will not be a service like ADP, but rather the tools that allow companies to 'roll their own' payroll, but we make it just as easy as paying ADP). Our timecard UI is highly interactive, visually pleasing, and graphical rather than the normal table of times and numbers.. of course you can flip the view to that if you like (which managers will want to do). After a timecard is approved, it is locked and cannot be edited unless first unlocked; and once payroll is processed it cannot be unlocked -- any mistakes that were made must be made up for in future payroll periods.

24. Budgets and Actuals. Managers and Producers can budget in fields that are hidden from non-management, they can budget in dollars, hours, weeks, or all of the above. They get 'actuals', or costs to date from timecards.

25. Ability to 'lock' records. Users with appropriate permission can 'lock' any row: every table has a lock as a default field, and those with permissions can 'lock' records, and they can only be 'unlocked' by someone with permissions. A timecard that gets processed through a payroll cannot be unlocked, this is a 'system lock', or 'locked by sytem'.

26. Two way street visibility of relationships: if a relationship, or 'link' exists, e.g. a Task is linked to a Shot, we automagically see a field on Shot called 'Tasks' that has a list of hyperlinked shots. General rule: any relationship field of any type (one to one, one to many, many to many) shows up in both places.

27. Modules. We have a FINANCE module that can be enabled by a company admin. This module allows the finance team to access a separate module with its own left NAV -- same UI and same functionality, but the workflow is very different and organized for a different team. Note: users can have permissions to both the regular left nav, or 'Production' view, and also access to the 'Finance' view. User toggle by clicking on their user icon in the upper right and switching views. The Finance module will have access to the Production tables, and can bring those Tables into their view, but no Finance tables can be seen from Production. Finance can create new fields on Production tables, but those but Finace tables -- like the general ledger -- will be firewalled in a top-of-class way, such that even big companies will have confidence that no confidential data will leak into the Production view. From the finance module the finance team: manages payroll, manages timecards (making rules for the different unions and classes of employees) manages the books, processes timecards, keeps track of HR confidential things like benefits, pay rates, etc.

28. Migration Assistant. Many potential clients will be overwhelmed by the real anxiety of switching so we will have an AI agent-assisted migration that is very well thought out: the agent will ask for the existing schema, or access to an api to thoroughly map a plan for migration, then the agent will migrate data and QA check for control numbers that match, and then suggest a QA process for new studios, and then run both systems in parallel, making our software a slave that gets updates in real time, and then once comfortable, clients can 'switch over' and make the new system the master, with the option of keeping the old system as the slave if they like.
